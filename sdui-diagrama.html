Cómo funciona un SDUI con Ktor BFF + Kotlin Multiplatform: un solo árbol de componentes serializado viaja del backend al cliente, que lo interpreta y lo pinta en Compose — en Android e iOS con el mismo código.

01 Tres módulos, un contrato

La pieza que lo hace todo limpio es :sdui-contract: una jerarquía sealed de DTOs @Serializable que viven en commonMain y que el servidor y el cliente importan literalmente la misma clase. Sin codegen, sin drift de esquema — el compilador es el test de contrato.

MÓDULO COMPARTIDO · commonMain

:sdui-contract CORAZÓN

Servidorimporta lo mismoCliente
  • sealed UiNode · column, row, text, image, button, lazyColumn…
  • sealed UiAction · navigate, setVar, network, submit…
  • UiModifier · padding, background, weight (tokens)
  • SduiEnvelope · schemaVersion + root + variables
  • SduiJson · la MISMA config de serialización en ambos lados
BACKEND · JVM

:server (Ktor BFF)

  • DSL de builders ensambla el árbol UiNode
  • Personalización, flags y A/B = ramas del builder
  • GET /screen/{id} → SduiEnvelope
  • POST /action → SduiPatch
  • Dueño del versionado y la capability negotiation
FRONTEND · Android + iOS

:composeApp (KMP)

  • Ktor client (OkHttp / Darwin por plataforma)
  • Render(node) recursivo — when sellado, en commonMain
  • UiModifier.toCompose() mapea a Modifier
  • VariableStore reactivo + dispatcher de acciones
  • UnknownNode = nunca crashea

04 Actualizar datos dentro de un componente

No todo cambio necesita volver al servidor. Hay cinco estrategias, según quién es dueño del dato. Elige una pestaña.

Variables / binding sin round-trip

El cliente puede calcular el cambio solo. Las acciones setVar / increment / toggle mutan un store reactivo local; los nodos con @{var} recomponen al instante. Para contadores, filtros, totales calculables, abrir modales.

↦ usuario toca + en el stepper
x increment("qty") → VariableStore
↻ nodos con @{qty} recomponen (texto, badge, total)
// el árbol lee la variable, no un valor fijo
{ "type":"iconButton", "icon":"icon.plus",
  "onClick":[ { "type":"increment",
                "name":"qty", "max":99 } ] }

{ "type":"text", "text":"@{qty} unidades" }
{ "type":"badge", "count":"@{qty}" }

Patch dirigido round-trip ligero

El servidor es dueño del dato (precio, stock, validación). Una acción network viaja, y el server responde un patch con operaciones por id: replace · updateProps · insert · remove · setVars. El cliente solo recompone los subárboles tocados.

↦ POST /cart/update { qty }
⟳ server recalcula precio + total
⤿ patch: replace lineTotal-42 · setVars cartTotal
// respuesta del server: solo lo que cambia
{ "schemaVersion":1, "changes":[
  { "op":"replace", "targetId":"lineTotal-42",
    "node":{ "type":"text",
            "text":"$ 12.990" } },
  { "op":"setVars",
    "values":{ "cartTotal":"$ 38.970" } }
]}

Input local + submit diferido

El input mantiene su valor con bind (UX fluida al instante) y dispara un network con debounce para que el server valide o reaccione. Búsqueda en vivo, validación de formularios.

⌨ usuario escribe → bind: queryVar (ya visible)
⏱ debounce 300ms → POST /search
⤿ patch: replace resultsList con hijos nuevos
{ "type":"searchBar", "bind":"queryVar",
  "debounceMs":300,
  "onChange":[
    { "type":"network",
      "endpoint":"/search",
      "payloadVars":["queryVar"] } ] }

Optimista + confirmación background

Para like / favorito / guardado: mutas la variable local ya (la UI cambia al toque) y disparas el network en paralelo. Si el server falla, el patch revierte la variable. Dos acciones en orden.

♥ toggle isFav → la UI ya cambió
↦ POST /items/42/favorite (en paralelo)
✓ ok: nada · error: patch revierte isFav
{ "type":"iconButton", "icon":"icon.favorite",
  "tintVar":"isFav",
  "onClick":[
    { "type":"toggle", "name":"isFav" },
    { "type":"network",
      "endpoint":"/items/42/favorite" } ] }

El cliente vuelve a pedir GET /screen/{id} y reemplaza todo el árbol. Para navegación, pull-to-refresh o cambios estructurales grandes — no para un solo valor.
